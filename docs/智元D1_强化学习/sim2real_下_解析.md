# 智元 D1 Sim2Real 全指南（下）解析

> 对应原文：`sim2real_下.pdf`，共 24 页。本文聚焦两件事：如何用 TensorBoard 诊断策略质量，以及如何把推理与 Lowlevel 控制迁移到 Jetson Orin。它不是逐字转写；原文中的版本、IP、接口名和硬件参数均应按现场环境复核。

## 1. 一页结论

下篇把 Sim2Real 从“一次真机实验”扩展为持续迭代的工程闭环：

```text
真机现象
  -> 排除控制链错误
  -> 读取训练日志
  -> 判断能力短板与训练稳定性
  -> 修改地形、奖励、动作边界和命令分布
  -> 增量训练
  -> 仿真复验
  -> 桌面端真机验证
  -> Jetson Orin 机载部署
  -> 收集新的真机证据
```

全文最关键的三个观点是：

1. 总奖励上升不能证明每种能力都在变好，必须拆看奖励项、终止原因、真实误差和训练性能。
2. 配置修改必须针对日志暴露的短板，例如打滑、停不住、转向误差或台阶通过性，而不是同时乱改所有 reward。
3. Orin 部署不是“把程序复制过去”这么简单，而是把供电、网络、输入、推理和控制收敛到机载系统，并重新验证时延、散热与可靠性。

## 2. 什么时候应该回到训练侧

上篇先解决 frame、四元数、关节映射、默认姿态、控制频率和部署增益。只有当以下条件成立，才有资格用训练日志解释真机表现：

- 状态持续更新，数值与物理运动一致；
- 关节映射和方向正确；
- 零命令时策略行为具有可重复性；
- 控制周期和通信基本稳定；
- 动作没有被错误缩放或过早裁剪；
- 机器人表现是“不够好”，而不是“完全不按正确逻辑工作”。

否则，训练日志再漂亮也不能解释部署链的语义错误。

## 3. TensorBoard 诊断方法

原文在 Isaac Lab 目录下启动 TensorBoard：

```bash
./isaaclab.sh -p -m tensorboard.main --logdir=logs
```

然后访问：

```text
http://localhost:6006/
```

曲线平滑只用于帮助观察趋势，不能隐藏尖峰或替代原始数据。建议同时保留较低平滑度查看异常。

### 3.1 Curriculum：课程是否真的推进

原文观察到 `curriculum/terrain_levels` 先下降后上升：

- 初期策略能力不足，课程自动降低地形难度；
- 基础能力形成后，地形等级逐步提升。

这种趋势说明课程机制在响应策略能力。如果曲线长期不变，应检查：

- curriculum 是否注册并启用；
- 晋级/降级条件是否能被触发；
- reward 是否给出了跨过难度门槛的学习信号；
- 当前难度是否一开始就过高或过低。

不能简单认为“地形等级越高越好”。如果等级快速上升但终止率和误差恶化，课程可能推进过快。

### 3.2 Episode Reward：策略具体学会了什么

原文逐项观察到的信号可整理为：

| 指标 | 原文现象 | 工程解释 |
|---|---|---|
| `action_rate_l2` | 仍偏高 | 动作变化快，平滑性不足 |
| `ang_vel_xy_l2` | 逐步改善 | 横滚/俯仰扰动在减小 |
| `contact_forces` | 较稳定 | 接触冲击没有明显恶化 |
| `feet_air_time` | 波动较大 | 步态节奏和落脚时序仍不稳定 |
| `feet_height_body` | 趋势不稳定 | 足端相对机身高度尚未收敛 |
| `feet_slide` | 持续存在 | 支撑期仍有打滑 |
| `feet_stumble` | 偶发 | 有绊碰，但当时不是主矛盾 |
| `joint_acc_l2` | 偏大 | 关节动作较猛，潜在冲击和能耗问题 |
| `joint_mirror` | 较好 | 左右对称性总体正常 |
| `joint_pos_limits` | 偶尔出现 | 部分动作逼近关节边界 |
| `joint_pos_penalty` | 仍较大 | 姿态经常偏离参考区间 |
| `joint_power` | 持续下降 | 能耗趋势在改善 |
| `joint_torques_l2` | 偏高 | 力矩使用仍不克制 |
| `lin_vel_z_l2` | 下降 | 竖直方向抖动减小 |
| `stand_still` | 波动明显 | 零命令静止质量一般 |
| `track_ang_vel_z_exp` | 改善但不稳 | 转向跟踪仍弱 |
| `track_lin_vel_xy_exp` | 提升明显 | 平面速度跟踪在增强 |
| `undesired_contacts` | 仍存在 | 非足端或不期望部位接触 |
| `upward` | 长期稳定 | 总体能够保持直立 |

由此得到的不是“策略好/坏”二元结论，而是一张能力画像：已经会走，基本不失控，但步态平滑、静止、转向和足端行为仍需改进。

### 3.3 Episode Termination：失败是怎样发生的

原文中：

- `time_out` 占多数，说明大部分 episode 能正常跑满；
- `terrain_out_of_bounds` 很低，说明极少跑飞或冲出边界。

因此当时的核心已不是“学不会走”，而是“走的品质还不够好”。

终止项应按比例而不是只看绝对计数，并与 curriculum 等级联合分析。随着难度提升，某种终止增加可能是合理过渡；在固定难度下持续增加才更像退化。

### 3.4 Loss：优化过程是否稳定

| 指标 | 原文解读 | 需要警惕的情况 |
|---|---|---|
| `entropy` | 持续下降，探索减少 | 过快降到很低可能过早收敛 |
| `surrogate` | 整体平稳 | 持续大幅振荡可能更新不稳定 |
| `value` | 基本稳定，偶发尖峰 | 尖峰频繁且越来越高可能价值网络失配 |
| `learning_rate` | 正常衰减 | 异常跳变或过早降至极低 |

`value` 尖峰可能发生在课程升级、命令分布改变或状态分布迁移时。单个尖峰不是失败证据，关键看它能否回落以及是否伴随 reward、termination 同步恶化。

### 3.5 Metrics：任务真实误差

原文指出：

- `error_vel_xy` 在下降但仍偏大；
- `error_vel_yaw` 仍高，转向明显弱于直行。

Metrics 比奖励更接近用户真正关心的任务效果。一个重要校验是：

```text
奖励改善 + 真实误差下降 -> 目标大体一致
奖励改善 + 真实误差不降 -> reward 可能被“钻空子”或与任务错位
```

### 3.6 Perf：问题来自算法还是系统吞吐

原文中的 `collection_time`、`learning_time` 和 `total_fps` 较稳定，说明采样与训练系统没有明显瓶颈。因此训练质量问题应优先从环境、奖励和任务分布排查。

如果 Perf 剧烈波动，则应先查：

- GPU/CPU 利用率和显存；
- 环境 reset 或传感器计算是否出现长尾；
- 日志、渲染和视频录制开销；
- 并行环境数与硬件是否匹配。

### 3.7 Policy 与 Train：总体是否还在进步

原文观察到：

- `mean_std` 仍有波动，策略仍在探索但尚未完全定型；
- `mean_episode_length` 长期接近跑满；
- `mean_reward` 和 `mean_reward/time` 持续上升。

综合判断：策略不是“没有学会”，而是已有基本能力，需要针对稳定性、停稳、转向和足端行为继续优化。

## 4. 从日志回到配置

### 4.1 增加针对性地形

原文提高 `pyramid_stairs` 和 `pyramid_stairs_inv` 的采样比例，并把台阶高度集中到约 0.13～0.15 m。

其目的不是追求更随机，而是增加与目标任务高度相关、难度可控的训练样本。对台阶任务，有效分布通常比“大杂烩地形”更能提供稳定学习信号。

风险是过拟合单一台阶尺寸。更稳妥的做法是保留一定连续分布，并在独立验证集上测试未见过的高度、摩擦和边缘形状。

### 4.2 收紧训练期动作裁剪

原文把 `joint_pos.clip` 从非常宽的 `(-100, 100)` 收紧到 `(-3, 3)`。

含义是让策略在训练时就面对更接近真实执行器的动作域，减少部署时才突然加入强裁剪造成的分布变化。它和上篇“部署侧可能适度放宽过窄裁剪”并不矛盾：

- 训练期不能宽到近乎无约束；
- 部署期也不能窄到把正常策略输出大量截断；
- 最终应让训练和部署动作边界一致，并用真实机械与安全边界确定数值。

### 4.3 重新定义机身稳定

原文的调整思路是：

- 减弱 `lin_vel_z_l2` 惩罚，允许跨障时保留必要的上下运动；
- 增强 `ang_vel_xy_l2` 惩罚，更重视横滚与俯仰稳定；
- 启用 `base_height_l2`，目标高度约为 0.40 m，抑制跨障时塌腰。

这体现了 reward 设计中的关键区别：稳定不等于完全不动。跨台阶时竖直运动是任务所需，真正应压制的是失控的姿态摆动和持续高度塌陷。

### 4.4 强化零命令静止

原文提高 `stand_still` 权重，把 command threshold 设在约 0.06，并加入零命令下的线速度与 yaw 角速度惩罚。

训练目标被拆成：

- 零命令时不小碎步；
- 不原地缓慢旋转；
- 机体速度真正接近零。

它解决了真实体验中很突出的“没有命令却一直微动”问题。阈值不能设成绝对零，否则传感器噪声和浮点抖动可能让策略持续受到惩罚。

### 4.5 自适应足端离地

原文用 `AdaptiveFeetClearanceReward` 替代固定抬腿高度，并让目标离地需求与命令、接触和坐标系相关。

核心思想是：

```text
平地/低速 -> 较低抬脚，节能且平稳
台阶/较高运动需求 -> 增加足端余量，减少绊碰
异常接触 -> 根据 stumble 等信号调整惩罚
```

固定高度很难同时兼顾平地效率和障碍通过性，自适应目标更符合任务条件变化。实现时必须确认足端高度使用 world frame 还是 body frame，以及地形基准如何定义。

### 4.6 重写命令分布

原文关闭绝对 heading command，直接训练：

- `lin_vel_x`：前后速度；
- `lin_vel_y`：横向速度；
- `ang_vel_z`：转向角速度。

同时将 `rel_standing_envs` 提高到 0.15，即约 15% 环境专门练习零命令站立。

这让训练分布明确覆盖“会走”和“能停”。命令分布就是任务定义的一部分；如果训练中几乎没有零命令样本，部署时要求机器人安静站立并不合理。

## 5. 增量训练结果怎样理解

原文复训后观察到：

- 线速度和 yaw 跟踪奖励明显提升；
- `upward` 稳定，直立性保持较好；
- `feet_slide` 和 `feet_stumble` 仍提示打滑、绊碰；
- `stand_still` 虽趋稳，但数值反而有所下降。

这说明修改方向有效，但不是所有目标同步改善。策略更偏向速度执行后，静止品质可能让位，这就是多目标 reward 的权衡。

正确的迭代方式是：

1. 每轮只围绕少数假设修改配置；
2. 保留基线 run 和固定评测场景；
3. 比较任务指标，不只比较 reward；
4. 在仿真、桌面端真机和 Orin 端分别复验；
5. 记录哪些能力改善、哪些能力退化。

## 6. Jetson Orin 迁移解析

### 6.1 迁移后的系统边界

桌面调试阶段：

```text
键盘/手柄 -> 桌面工作站 -> policy -> UDP Lowlevel -> D1
```

机载阶段：

```text
外接手柄 -> Jetson Orin -> 速度命令 -> policy
         -> Lowlevel 控制下发 -> D1 执行
```

Orin 同时承担输入、推理和命令下发，使系统不再依赖桌面主机，也为后续加入视觉、状态估计和本地规划提供自然的计算边界。

### 6.2 系统烧录

原文使用 NVIDIA SDK Manager：

```bash
sdkmanager

# 需要历史版本时
sdkmanager --archived-versions
```

操作要点：

1. 短接 `FC REC` 与 `GND`，使 Orin 进入 Recovery 模式；
2. 用 USB 3.0 连接 Orin Type-C 与主机；
3. 在 SDK Manager 中选择 Jetson Orin NX 和适配的 JetPack；
4. 不要误勾选主机驱动更新，以免破坏开发主机环境；
5. 原文建议 Runtime 和 SDK 组件都安装，以便后续 CUDA/TensorRT 开发；
6. 若刷写阶段连接失败，可暂时关闭主机其他以太网连接，避免 USB 虚拟网卡路径冲突。

版本选择不能只看“最新”，必须与要使用的 CUDA、cuDNN、TensorRT、ONNX Runtime 或 LibTorch 兼容。

### 6.3 有线网络拓扑

原文示例：

```text
D1 调试口:  192.168.168.168/24
Jetson Orin: 192.168.168.169/24
```

D1 有线调试口没有 DHCP，Orin 必须设置同网段静态地址。

登录 D1：

```bash
ssh firefly@192.168.168.168
```

修改 SDK 目标地址：

```bash
sudo vim /opt/export/config/sdk_config.yaml
```

把 `target_ip` 从回环地址改为 Orin：

```yaml
target_ip: "192.168.168.169"
```

再检查运动控制启动脚本：

```bash
sudo vim /opt/app_launch/start_motion_control.sh
```

原文示例要求：

```bash
export SDK_CLIENT_IP="192.168.168.168"
```

这里是 D1 自身地址，而不是 Orin 地址。

最后编辑 systemd 服务：

```bash
sudo vim /etc/systemd/system/robot-launch.service
```

增加网卡绑定：

```ini
Environment="ROBOT_NET_INTERFACES=eth0"
```

> `eth0` 只是原文示例。必须用 `ip link`/`ip addr` 确认当前固件中的真实接口名，不能盲抄。

原文特别提醒：切换有线模式后，D1 启动运控时要求调试口处于物理载波在线状态。网线未连接时运控可能无法拉起，因此这种模式更适合固定连接，不适合频繁拔插。

### 6.4 供电与机械连接

原文称示例 Orin 的输入范围约为 5～19 V，并从 D1 机身 12 V 供电口经 XT30 引出电源，网络则直连 D1 调试口。

这里必须按具体载板核验，而不是只按模组名称判断：

- 输入电压范围、峰值功耗和启动浪涌；
- D1 12 V 端口持续/峰值电流能力；
- 保险、反接和过流保护；
- 线径、接头额定电流和应力释放；
- Orin 满载散热条件；
- 安装支架强度、重心变化和振动隔离。

原文临时固定方案适合短时验证链路，不应直接视为长期可用的机械部署方案。

### 6.5 输入链路

D1 不能直接把手柄输入转发给 Orin，因此原文修改 `rl_real_d1.py`，让手柄直接接到 Orin，由 Orin 生成策略需要的速度和转向命令。

> 文件名校勘：原文此处确实写作 `rl_real_d1.py`，但配套框架篇展示的 D1 实机控制主体是 `rl_real_d1.hpp/.cpp`。这可能是作者在 Orin 侧额外编写的 Python 包装程序，也可能只存在于其定制分支；实施时应以当前仓库实际入口为准，不能假定上游必然包含该 `.py` 文件。

输入层还应处理：

- 死区和摇杆漂移；
- 命令限速和斜坡；
- 手柄断连时自动归零；
- 急停/阻尼按键的最高优先级；
- 输入时间戳和超时。

## 7. Orin 上必须重新验证的指标

模型相同不代表行为一定相同。迁移后至少测量：

| 类别 | 指标 |
|---|---|
| 推理 | 平均、P95、P99 和最大推理时延 |
| 控制 | 周期抖动、deadline miss、命令陈旧度 |
| 网络 | 丢包、乱序、往返时延、断线恢复 |
| 资源 | CPU/GPU/内存利用率、功耗、温度、降频 |
| 输入 | 手柄噪声、断连响应、命令更新率 |
| 机械 | 支架松动、线缆拉扯、重心改变后的步态 |
| 长稳 | 连续运行时间、热稳态、异常退出后的安全状态 |

如果在桌面端稳定、Orin 上却抖动，优先检查时序、线程调度、推理后端和热降频，不应立即重训策略。

## 8. 诊断决策表

| 证据组合 | 更可能的问题 | 下一步 |
|---|---|---|
| reward 上升，metrics 误差下降 | 学习方向正确 | 继续验证泛化和真机 |
| reward 上升，metrics 不改善 | reward 与任务错位 | 重审权重和可被利用的奖励 |
| episode 多数 timeout，但步态差 | 品质问题 | 调足端、平滑、能耗和静止 reward |
| termination 快速恶化 | 基础稳定性或课程过快 | 回退难度，查姿态/接触与更新稳定性 |
| value 偶发尖峰后恢复 | 分布变化适应 | 观察即可，结合课程分析 |
| value 尖峰持续放大 | 训练不稳定 | 查学习率、归一化、奖励尺度和课程跳变 |
| Perf 稳定但效果差 | 环境/奖励/命令分布 | 从任务建模侧排查 |
| Perf 波动且效果同步波动 | 系统瓶颈 | 先修采样、硬件或仿真性能 |
| 桌面端好、Orin 端差 | 部署时序/资源问题 | 测推理长尾、控制抖动和热降频 |

## 9. 对原文方法的补充与局限

1. **缺少统一评测集**：训练曲线不能代替固定地形、固定命令和固定随机种子的回归评测。
2. **reward 数值需谨慎解释**：不同项的符号、归一化和 episode 累积方式不同，不能只比较曲线绝对大小。
3. **修改存在耦合**：地形、命令和多个 reward 同时改变后，很难归因；推荐消融实验。
4. **Orin 软件运行细节不足**：原文没有完整给出交叉编译/本机编译、推理后端、systemd 服务和进程守护方案。
5. **安全链仍需补齐**：手柄断连、进程崩溃、网络中断、过温和低电压都应触发可验证的安全状态。
6. **网络配置有设备依赖**：IP 和接口名只适用于示例，固件更新后也可能变化。
7. **供电结论不能泛化**：Orin NX 模组、开发套件和第三方载板的电气要求可能不同，必须查具体硬件手册。

## 11. 最终理解

下篇的主线不是“调几个 reward，再刷一台 Orin”，而是建立两个闭环：

```text
学习闭环：现象 -> 日志证据 -> 配置假设 -> 复训 -> 固定评测
部署闭环：工作站验证 -> 机载迁移 -> 时序/资源测量 -> 真机证据 -> 再迭代
```

当团队能够稳定重复这两个闭环，Sim2Real 才从一次成功演示变成可持续维护的机器人系统。
