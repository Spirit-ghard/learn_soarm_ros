# 智元 D1 Sim2Real 全指南（上）解析

> 对应原文：`sim2real_上.pdf`，共 24 页。本文不是逐字转写，而是对其控制接入、首次真机部署和部署侧调参方法的结构化解析。PDF 为图片型文档，命令和关键配置已结合页面图像复核；实际操作仍应以当前代码、SDK 和机器人固件为准。

## 1. 一页结论

这篇文章真正要解决的不是“怎样加载一个 `.pt` 模型”，而是怎样证明从策略到电机的整条链路语义一致、时序连续且可安全退出。

核心链路可以概括为：

```text
D1 Lowlevel 状态
  -> SDK 数据解包
  -> 统一 RobotState
  -> 训练期同构的观测向量
  -> 策略推理
  -> 动作缩放 + 默认姿态
  -> PD 控制与力矩限制
  -> 关节/腿序映射
  -> 关节位置限位
  -> D1 Lowlevel 命令
```

文章最重要的工程判断有五个：

1. 强化学习策略需要关节级闭环，应走 `Lowlevel`，不要在同一进程里混用 `Highlevel` 和 `Lowlevel`。
2. 推理频率不等于底层发包频率。D1 需要连续的高频控制流，因此应把策略环和控制环解耦。
3. “上电打架”通常先查坐标系、四元数、关节映射和默认姿态，不应先归咎于 reward。
4. “能走但不够好”才进入部署侧微调，优先看动作裁剪、`action_scale`、`rl_kp`、`rl_kd` 和力矩限制。
5. 第一次真机测试的目标是验证链路，不是追求速度或展示效果。必须保留快速回到阻尼模式的手段。

## 2. 为什么训练收敛不等于完成

仿真策略只在训练环境定义的状态、动作和动力学语义中成立。真实系统额外引入：

- IMU 和关节反馈噪声；
- 通信、推理、线程调度和执行器延迟；
- 质量、阻尼、摩擦、接触与电机响应误差；
- 训练中可直接获得、真机中却难以可靠测得的状态量；
- 控制指令丢包、超时和不连续。

因此 Sim2Real 的本质是验证两个等价关系：

```text
部署期观测的物理含义 == 训练期观测的物理含义
部署期动作的执行含义 == 训练期动作的执行含义
```

任何一侧不等价，策略即使在仿真里表现优秀，也会在真机上接收到“另一道题”。

## 3. D1 控制架构解析

### 3.1 Robot Interface 的位置

D1 不是一组可以被应用层任意直连的电机。APP、手柄、SDK 和应用能力先进入 `Robot Interface`，再由它对接运动控制、命令接口、状态预处理以及相机、IMU、算力平台和执行机构。

这意味着二次开发必须服从平台已有的软件分层和控制权约束。

### 3.2 Highlevel 与 Lowlevel

| 接口 | 控制语义 | 典型用途 | 是否适合 RL 策略落地 |
|---|---|---|---|
| Highlevel | 调用机器人已有运动能力 | 原生步态、整机能力调用 | 通常不适合关节级策略 |
| Lowlevel | 读取底层状态并下发关节命令 | 自定义控制器、RL policy | 适合，但安全责任转移到开发者 |

强化学习策略通常每个周期输出 12 个关节的目标位置，并配合目标速度、`kp`、`kd` 和前馈力矩。因此文章选择 Lowlevel 是控制语义决定的，而不是单纯追求“更底层”。

### 3.3 Lowlevel-only 的理由

如果原生运控和策略同时拥有输出权，系统可能出现两个控制器争夺同一组关节的情况。文章因此把进程锁定为 Lowlevel-only。

它牺牲了运行期快速调用部分高层能力的便利，但换来了：

- 控制权唯一；
- 状态转换更可预测；
- 故障定位边界更清楚；
- 避免高低层模式切换延迟。

这里的原则是：真机调试首先追求确定性，而不是功能数量。

## 4. 双频控制结构

原文实现包含三类循环：

| 循环 | 原文示例节奏 | 职责 |
|---|---:|---|
| `loop_keyboard` | 约 20 Hz | 接收键盘/手柄输入 |
| `loop_rl` | `dt * decimation` | 构造观测并运行策略 |
| `loop_control` | 0.002 s，即 500 Hz | 持续读取状态、执行 FSM、发送最新命令 |

控制周期与策略周期的关系为：

```text
T_policy = dt * decimation
f_policy = 1 / T_policy
```

以文章给出的 `dt = 0.005`、`decimation = 4` 为例，策略频率为 50 Hz；底层控制流则按 500 Hz 发送。策略每 20 ms 产生一次新目标，控制环在此期间反复发送当前最新目标。

```text
策略线程（生产者）  50 Hz:  action_0 -------- action_1 -------- action_2
                                 |                  |
控制线程（消费者） 500 Hz:  a0 a0 a0 ... a0   a1 a1 a1 ... a1
```

这解决了两个问题：

- 策略仍按训练期节奏运行，不因真机接口而改变时间尺度；
- D1 底层不会因为推理间隔而出现命令断档。

实现时还应补充考虑线程安全：动作或命令的共享对象应采用互斥锁、无锁队列或原子快照，避免控制线程读到更新一半的数据。

## 5. 状态上行：从 SDK 到策略观测

原文从 Lowlevel 获取三类核心数据：

- 电机状态：关节位置、速度及力矩估计；
- IMU 四元数；
- 机体角速度。

这些数据先进入统一的 `RobotState<float>`，再由公共 RL 逻辑构造观测。适配层的价值是把“D1 SDK 怎样组织数据”和“策略需要什么语义”隔离开。

### 5.1 观测一致性检查

逐项核对以下内容：

| 项目 | 必须确认的内容 | 错误表现 |
|---|---|---|
| 四元数 | 分量顺序是 `wxyz` 还是 `xyzw`；方向定义 | 姿态方向错误、向一侧倒 |
| 角速度 | body frame 还是 world frame；单位是否为 rad/s | 原地对抗、转向异常 |
| 关节顺序 | FR/FL/RR/RL 和 abad/hip/knee 的排列 | 各腿动作串线、上电打架 |
| 关节方向 | 正方向与训练模型是否一致 | 单关节或单腿反向 |
| 关节单位 | rad 还是 degree | 输出数量级灾难性错误 |
| 默认姿态 | 与训练的 reference pose 相同 | 所有关节观测存在固定偏置 |
| 观测顺序 | 与导出模型的输入拼接顺序相同 | 网络输出无规律 |
| 缩放与裁剪 | 与训练期一致 | 网络工作在错误数值分布 |

### 5.2 角速度坐标系的关键校勘

上篇明确指出：如果策略由 `robot_lab` / Isaac Lab 训练，`root_ang_vel_b` 已经是机体系角速度，D1 代码通过 `getBodyGyro()` 得到的量也应按实际 SDK 语义验证；若输入已是 body frame，应设置：

```cpp
this->ang_vel_axis = "body";
```

只有 SDK 返回 world-frame 角速度时，才应通过四元数逆旋转到机体系。

> 注意：配套的 `sim2sim.pdf` 示例代码却写了 `ang_vel_axis = "world"`。两份材料在这一点上互相冲突，不能照抄常量。正确做法是查当前 SDK 文档并做静态旋转实验：机器人保持不动、分别绕机体 X/Y/Z 轴转动，核对三轴符号和坐标系，再决定是否旋转。

### 5.3 默认姿态不是普通初始值

部署观测通常使用相对关节位置：

```text
q_relative = q_measured - q_default
```

所以 `default_dof_pos` 同时承担两个角色：

- 起身后的目标站姿；
- 策略观测中的关节零点。

如果训练和部署使用不同的默认姿态，策略从第一帧开始就会错误理解当前关节偏差。该问题不会触发通信或维度错误，但会系统性污染全部 `dof_pos` 观测。

## 6. 命令下行：从动作到 D1 电机命令

原文的动作输出可抽象为：

```text
a_scaled = clip(a) .* action_scale
q_des    = q_default + a_scaled
tau      = kp .* (q_des - q) - kd .* dq
tau      = clamp(tau, -tau_limit, tau_limit)
```

再将统一命令中的 `q`、`dq`、`kp`、`kd`、`tau` 映射到 D1 SDK 的每条腿、每个关节字段。

最终写入 SDK 前还应做物理关节位置限位：

```text
策略输出
 -> 动作裁剪
 -> 动作缩放
 -> 目标位置
 -> PD/力矩限幅
 -> 腿序与关节序映射
 -> 机械位置限位
 -> SDK 下发
```

动作裁剪、力矩限幅和机械位置限位不是同一种保护：

- 动作裁剪约束神经网络输出域；
- 力矩限幅约束执行强度；
- 位置限位约束机械可达范围。

三者应同时存在，且超限日志应包含腿、关节、原始值和裁剪后值。

## 7. 首次连接与运行流程

### 7.1 无线调试拓扑

```text
开发电脑（D1 AP 分配地址，例如 192.168.234.14）
        <------ Wi-Fi / UDP ------>
D1（示例地址 192.168.234.1）
```

原文给出的流程如下，地址必须替换为现场实际值：

```bash
# 在 rl_sar 根目录，以无 ROS 的 CMake 模式编译
./build.sh -m

# 连接 D1 AP 后登录机器人
ssh firefly@192.168.234.1

# 在 D1 上修改 SDK 目标地址
sudo vim /opt/export/config/sdk_config.yaml
```

将配置中的目标地址指向开发电脑，例如：

```yaml
target_ip: "192.168.234.14"
target_port: 43988
```

重启 D1 并重新连接后，在开发电脑运行：

```bash
./cmake_build/bin/rl_real_d1 192.168.234.14 192.168.234.1
```

预期看到类似：

```text
client bind success
connect success!
```

连接成功只证明 UDP/SDK 链路可用，不证明观测和动作语义正确。

### 7.2 第一次动作测试

原文键位如下：

| 键位 | 功能 |
|---|---|
| `0` | 从当前姿态插值到 `default_dof_pos` |
| `1` | 进入 RL 控制 |
| `P` | 立即回到阻尼/被动模式 |
| `W` / `S` | X 方向速度每次增减 0.1 m/s |
| `A` / `D` | Y 方向速度每次增减 0.1 m/s |
| `Q` / `E` | yaw 角速度每次增减 0.1 rad/s |

建议把首次测试拆为四个门槛：

1. 吊架或可靠保护下，只启动状态读取，检查静态姿态与关节值。
2. 进入阻尼模式，验证 `P` 和进程退出都能可靠卸力。
3. 执行起身插值，逐关节核对方向、目标与实测跟踪。
4. 零速度进入 RL，确认无对抗后才小步增加前进命令。

任何门槛不通过，都不进入下一阶段。

## 8. 现象驱动的部署侧微调

### 8.1 先判断是链路错误还是参数问题

| 现象 | 优先判断 |
|---|---|
| 方向基本正确，但不稳、不顺、不够快 | 链路大体成立，进入参数微调 |
| 上电打架、方向反、固定某腿错动 | 坐标系/映射/符号/默认姿态错误 |
| 动作随机且不可重复 | 观测顺序、维度、历史帧或模型输入错误 |
| 偶发跳变 | 数据竞争、丢包、状态时间戳或模型重载问题 |

### 8.2 运动指令不敏感

原文认为常见原因是 `clip_actions` 过窄，策略动作在进入控制链之前已经饱和。示例把上下限由约 `[-1.6, 1.6]` 放宽到 `[-3, 3]` 后，0.5 m/s 命令下的运动意愿增强。

解析：放宽裁剪不是通用加速按钮。应先记录动作饱和率：如果大量维度长时间贴住上下限，裁剪才可能是瓶颈；如果动作远未触顶，则应检查命令缩放、训练命令分布和速度观测。

### 8.3 “腿软”

优先看 `rl_kp` 与 `rl_kd`：

- `kp` 太低：位置误差恢复能力弱，支撑下沉；
- `kd` 太低：扰动后回弹和振荡明显；
- `kp` 过高而 `kd` 不足：动作僵硬、冲击和高频抖动；
- 力矩限幅过低：即使增益足够，实际输出仍被截断。

调参应小步进行，并同时看目标/实际位置、速度和力矩饱和情况，不能只凭肉眼判断“更有力”。

### 8.4 抬腿高度不足

原文建议检查并适度增大 `action_scale`。它决定归一化动作转换为关节角偏移的幅度。过小会导致步态有相位但幅度不足；过大则增加碰撞、超限和失稳风险。

应按关节类型分别调整，而不是统一放大 12 维动作。abad、hip、knee 的机械范围和步态作用不同，原文配置也采用不同尺度。

## 9. 故障定位表

| 现象 | 首查 | 验证方法 |
|---|---|---|
| 四腿互相“打架” | 腿序和关节序映射 | 单关节小幅命令，核对唯一响应关节 |
| 整机姿态反馈方向错误 | 四元数顺序/方向 | 手动绕三轴转动并记录姿态变化 |
| 原地旋转或转向相反 | 角速度 frame 和符号 | 分轴旋转实验，核对 body/world 变换 |
| 起身后立即偏置发力 | `default_dof_pos` | 比较训练和部署 12 维参考姿态 |
| 动作过猛 | `action_scale`、`kp`、力矩上限 | 查看动作和力矩饱和比例 |
| 指令响应弱 | 动作裁剪、命令缩放 | 记录裁剪前后动作与 command 向量 |
| 周期性抖动 | `kp/kd`、控制周期、丢包 | 画目标/实测位置和循环抖动直方图 |
| 偶发卡顿 | 推理阻塞控制环 | 分别统计推理耗时和控制环 deadline miss |
| 退出后仍发力 | 清零/阻尼命令不可靠 | 验证异常退出和信号处理路径 |

## 10. 对原文方法的补充与局限

原文非常适合建立首轮落地思路，但工程实施时还需补齐以下内容：

1. **实时性指标**：不仅设置频率，还应统计周期抖动、最大推理时延、队列陈旧度和丢包率。
2. **看门狗**：状态超时、命令超时、姿态越界、通信中断时应自动进入阻尼或安全状态。
3. **启动校验**：模型维度、观测列表、关节数、配置哈希不一致时拒绝进入 RL 状态。
4. **退出安全**：正常析构之外，还要覆盖 `SIGINT`、异常、线程崩溃和网络断开。
5. **数据记录**：至少记录时间戳、命令、IMU、关节状态、动作、目标位置、力矩和 FSM 状态。
6. **参数版本化**：训练配置、模型文件和部署配置应绑定版本，避免“模型正确、配置拿错”。
7. **数值不可盲抄**：文章中的增益、力矩、关节范围和 IP 都是示例，必须按当前 D1 型号、SDK、固件和策略核验。

- [ ] 核对 12 个关节的顺序、方向、零点与机械限位。

- [ ] 配置状态/命令超时和快速阻尼路径。
- [ ] 吊架下依次验证状态读取、阻尼、起身、零命令 RL。

## 12. 最终理解

这篇文章最有价值的地方，是给出了一个清晰的排错边界：

```text
系统性错误（打架、反向、串腿） -> 先修部署语义
品质问题（不稳、不顺、不够快） -> 再做部署参数微调
部署微调仍不能解决             -> 回训练日志与奖励设计
```

Sim2Real 上篇完成的是“让策略在真实硬件上回答同一道题”。只有这一步成立，后续讨论训练质量和嵌入式迁移才有意义。
